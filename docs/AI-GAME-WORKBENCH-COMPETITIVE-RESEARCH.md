# AI 游戏工作台竞品调研与游芽产品建议

调研日期：2026-09-13。用途：为游芽的产品定位、功能取舍和后续验证提供依据。

本报告基于公开官网、产品文档及本地项目说明进行案头调研，未登录付费产品、未实际生成竞品游戏，也未测试导出结果。功能公开可查不等于效果已经验证；“未确认”不等于产品没有该能力。目标用户归类和竞争强度是分析判断，非厂商用户构成统计。文中的建议尚未加入实施承诺。

## 1. 主要结论

AI 游戏工作台已经有直接竞品。最值得优先对标的是 Rosebud 的浏览器创作流程、GDevelop 的游戏对象与事件编辑，以及 Replit 的工程迭代与恢复机制。Astrocade 代表创作与消费结合的社区路线；Summer Engine 代表桌面引擎与 Agent 结合的路线；极逸 SOON 是值得持续核查的国内同类产品。[1][3][5][8][9][10]

“自然语言生成游戏”“模板”“素材生成”“先规划后修改”“版本回退”已经不是独有能力。Replit 还公开提供真实浏览器测试及回放，因此“有自动测试”也不足以构成差异。[3][6][7]

游芽值得验证的方向是：针对少数明确的 2D 玩法，在连续修改中保住既有规则，把需求、变更、测试和可带走的版本关联起来。这个方向是待验证的产品假设，不能据公开资料就声称竞争对手做不到。

当前不适合追赶全面 3D、多人联网、内容社区和多平台商店发布。现有工作台仍需要本地安装、Docker 和模型配置；面向大众创作者时，这些成本可能抵消“自然语言做游戏”的便利。早期应优先服务有基础技术能力的独立创作者与小团队策划。

## 2. 竞争范围

| 类型 | 本次重点产品 | 用户实际购买的价值 | 与游芽的关系 |
| --- | --- | --- | --- |
| 浏览器 AI 游戏创作 | Rosebud、Astrocade | 快速获得可玩作品、分享与继续修改 | 直接争夺首次创作和轻量迭代需求 |
| 游戏引擎内 AI 创作 | GDevelop、Summer Engine | 生成之后仍能用引擎编辑、调试和发布 | 争夺希望持续开发的创作者 |
| 国内游戏垂类平台 | 极逸 SOON | 游戏制作流程、素材、数值与品控 | 方向相近，需补充实际产品核验 |
| 通用 AI 开发平台 | Replit | 代码、运行环境、测试、协作和部署 | 对有技术基础的用户是强替代方案 |
| 游戏素材与设计工具 | Ludo.ai、Scenario | 更快得到能用于项目的素材 | 局部竞争，同时可成为能力供应商 |

即梦、可灵等通用视觉生成工具主要覆盖内容生产环节。对本项目而言，Ludo.ai 和 Scenario 更值得用于研究游戏素材的规格、动画、风格和 API 接入。[11][12][13][14]

OpenGame 在既定方案里承担编码执行器角色，与最终用户使用的完整工作台处于不同层级。评估是否复用其技术，与评估用户是否会选择游芽，需要分开进行。[16]

## 3. 八个重点产品

### 3.1 Rosebud：最直接的浏览器创作对标

官方页面提供描述需求、图片上传和模板入口；产品介绍明确包含可编辑 JavaScript、对话迭代、浏览器试玩、素材生成、网页发布和 Windows 打包。当前首页展示 RPG、幸存者类、互动故事等入口；部分其他模板标注 Coming Soon，不能全部记为已开放。[1][2]

**目标用户判断：** 希望快速做出可分享作品的个人创作者、游戏爱好者，以及愿意通过代码继续完善的独立开发者。

**竞争影响：** 游芽不能将“能修改”“能看代码”“能生成素材”描述为 Rosebud 缺失的能力。其公开创作与交付范围已经比游芽当前四种固定 Canvas 模式更广，但生成质量和连续修改可靠性未经本次实测。

**值得借鉴：** 把模板、描述需求和参考图放在同一入口；第一轮完成后立即试玩；通过局部修改继续创作。不要让用户先理解内部角色编排才能开始。

**待核验：** Windows 打包所含依赖、完整工程导出与离线运行条件、历史恢复粒度、现有外部项目导入能力。官网说明能编辑代码和打包，不足以证明任意项目都能无损迁出。

### 3.2 GDevelop：最值得研究的游戏编辑范式

当前官方文档说明，AI 可读取和修改场景、对象、行为、变量、事件与特效，也能查找官方扩展和素材。复杂任务会显示计划与步骤；Auto edit 关闭时，修改前逐次确认。云项目会在消息和 AI 请求前保存恢复点，文档明确本地项目不具备同样的自动恢复能力。[3]

其官网及套餐页还展示可视化编辑、游戏预览、多平台导出、素材商店、玩家反馈等能力。AI 用量和云服务按套餐区分；老博客的额度说法与当前文档存在差异，应以当前套餐和实际账号界面为准。[4]

**目标用户判断：** 愿意掌握基础引擎概念的初学者、独立开发者、教育用户，以及需要逐步完成完整作品的人。

**竞争影响：** “计划确认、持续修改、版本恢复”不能作为游芽独占能力。它的关键启发是让 AI 操作游戏对象和规则，用户仍能理解和修改结果。

**值得借鉴：** 塔、敌人、波次、角色跳跃、卡牌费用等应成为受控配置或明确扩展点；把“讨论方案”和“开始修改”区分开；将简单调参保持为短流程。

**待核验：** 多次增加机制后原有规则保留情况、复杂交互的错误恢复、具体玩法的自动测试覆盖。官方文档仍要求使用者复核 AI 结果。

### 3.3 Replit：不能忽略的通用平台替代

Replit 已设置 AI 游戏构建场景页，描述平台跳跃、跑酷、策略和互动故事等应用，并提供对话修改、实时协作及部署流程。[5] 工程文档明确提供 checkpoints/rollback；App Testing 可使用浏览器进行交互测试、回放和自我修正，但支持范围有技术栈限制，也并非每条用户消息后必测。[6][7]

**目标用户判断：** 前端开发者、技术型创作者，以及制作带登录、数据库或其他 Web 功能游戏原型的小团队。

**竞争影响：** 对技术型用户，“通用开发 Agent + 游戏模板 + 测试脚本”是很现实的替代方案。游芽增加角色数量或更多模型选择，未必足以让这些用户迁移。

**值得借鉴：** 任务级恢复点、每次变更的描述、测试回放、失败定位和可见用量。游芽的检验重点应深入玩法，例如重复升级是否重复扣费、回合是否卡死、重开后旧敌人是否残留。

**待核验：** 浏览器测试对实时 Canvas 输入、连续跳跃、波次逻辑和游戏数值约束的实际覆盖。通用 Web 自动测试不能直接等同于游戏规则验收。

### 3.4 Astrocade：创作与试玩社区对标

官方定位包含创建、分享、游玩 AI 游戏。创作者指南涵盖画面比例、碰撞范围、镜头、动作反馈、分层和性能，并建议短修改、多轮试玩与回退。[8]

**目标用户判断：** 游戏爱好者、内容创作者，以及主要希望在平台上创作和传播作品的人。

**竞争影响：** 用户要的是“做完有人玩”时，作品分发和反馈可能比导出文件更有吸引力。游芽当前没有公开在线工作台演示和公网发布链路，在这一场景存在明显门槛。

**值得借鉴：** 试玩反馈直接变成下一轮修改；将手感、受击反馈、重开等纳入引导。初期可通过邀请式用户测试观察需求，不必立即建设公共内容社区。

**待核验：** 源码下载、站外独立运行、付费权益和恢复机制细节。本次未找到充分的官方导出文档，不能据第三方比较表断言“不支持导出”。

### 3.5 Summer Engine：桌面引擎与 AI 结合

官网展示通过对话制作 2D/3D 场景、编辑 GDScript、使用素材、实时预览及按目标平台准备导出，并提供 MCP 连接外部编码工具。页面明确现有项目需要单独做兼容性检查，导出仍涉及工具链、签名及提交审核。[9]

**目标用户判断：** 愿意安装桌面工具、需要深入场景编辑和继续开发的独立创作者。

**竞争影响：** 本地工作流与可编辑工程也有竞品覆盖。若游芽转向完整引擎编辑器，将面临远大于当前模板工作台的功能范围和维护负担。

**值得借鉴：** 让 Agent 通过明确工具操作工程；保留人工审查与运行验证；模型入口和引擎能力解耦。

**待核验：** 真实项目兼容性、MCP 权限与稳定性、资源导入及各导出目标。不能因为使用 GDScript 就认定任意 Godot 项目可直接迁移。

### 3.6 极逸 SOON：国内垂类平台观察对象

其官网可确认游戏垂类定位、SOON-fx 数值引擎入口、作品案例，以及按图像、性能、布局、手感、数值体验进行评分的品控展示。官网的 AP 等级属于厂商自定义体系，不能作为行业统一标准或独立质量认证。[10]

**目标用户判断：** 中文游戏创作者、策划以及关注素材、数值与制作流程的团队；实际客户构成未核实。

**竞争影响：** “中文游戏制作”“工作流”“质量控制”本身也不足以建立独占定位。其数值和品控呈现方式值得进一步体验。

**值得借鉴：** 把数值与手感列为单独验收维度，例如塔防的一局时长、不同塔的使用情况、资源是否过剩；不要只显示编译通过。

**待核验：** 登录后的实际编辑能力、完整工程导出、连续修改、开放 API、套餐和商用条件。公开报道中的“全球唯一”“替代数月开发”等宣传不足以支撑本报告的比较结论。

### 3.7 Ludo.ai：游戏素材与设计能力供应商

当前功能页重点包括精灵图、精灵动画、图像、3D、音频、视频与游戏设计辅助；API/MCP 文档公开列出程序化素材生成。历史更新记录存在 Playable Generator，但当前功能主导航未突出这一入口，本报告不据旧内容将其认定为当前完整游戏工作台。[11][12]

**目标用户判断：** 缺少美术或音频产能的独立开发者，以及已有项目、需要补充素材的团队。

**值得借鉴：** 素材类型和动画规格、生成历史、异步任务、防止重试重复扣费、生成结果及时入库。将素材的来源和游戏中的使用位置关联起来。

**复用边界：** 本次页面显示 API/MCP 从 Pro 开放，标示为 50 美元/月；免费试用和 Indie 不开放 API/MCP，API 调用仍消耗额度。此为访问时页面口径，不是报价承诺。既有 100 元实验预算不应直接承担这项订阅。[12]

### 3.8 Scenario：成套风格与素材流程对标

游戏行业页展示角色变体、素材换装、多方向精灵、卡牌和界面相关流程；API 页面说明可程序化接入素材生成、模型训练和内容管理，并提供执行前成本估算能力。API 入口要求相应付费套餐。[13][14]

**目标用户判断：** 重视统一画风、批量素材和持续内容更新的美术团队与游戏工作室。

**值得借鉴：** 同一项目的风格说明、参考素材、成套资产生产和选用；先估算再生成；保留资源版本与引用关系。

**复用边界：** API 可用性不等于接入后素材一定可直接用于游戏。透明背景、角色比例、朝向、帧尺寸和资源加载仍需游芽验证。首期可先实现统一素材协议，再比较供应商，避免绑定某家的工作流。

## 4. 围绕用户任务的能力对照

表内是公开证据概括，不是评分排名；不同产品的“支持”不代表相同质量或相同交付形态。

| 产品 | 首次获得可玩内容 | 持续修改 | 素材 | 验证与恢复 | 交付与分发 |
| --- | --- | --- | --- | --- | --- |
| Rosebud | 描述或模板生成 | 对话迭代、JavaScript 编辑 | 公开提供美术与音频生成 | 试玩明确；规则回归证据未确认 | 网页发布、Windows 打包；工程迁出条件待测 |
| GDevelop | 在项目内生成机制 | 对象、场景、事件、参数 | 素材商店及 AI 查找官方资源 | 预览；云项目 AI 恢复点 | 多平台导出与 gd.games |
| Replit | 自然语言构建 Web 游戏 | 工程代码和对话迭代 | 游戏场景页宣称支持 | checkpoints、浏览器测试和回放；玩法深度待测 | Web 部署；工程迁出需实测 |
| Astrocade | 描述生成平台内作品 | 指南明确短修改和回退 | 指南涉及精灵、动画及分层 | 强调反复试玩；自动规则检查未确认 | 平台内发布和消费；站外导出未确认 |
| Summer Engine | 对话辅助场景与脚本 | GDScript、场景及 Agent 工具 | 内置生成和导入入口 | 本地测试流程；自动验收深度待测 | 桌面等目标平台的导出流程 |
| SOON | 官网有作品案例 | 本次公开证据不足 | 细节需产品内核验 | 数值与品控展示；独立结果未核验 | 工程导出与发布条件待核验 |
| Ludo.ai | 本次不认定完整游戏生成主流程 | 素材与设计迭代 | 精灵、动画、音频、3D 等 | 素材任务与历史，不等于玩法测试 | 素材输出、API/MCP |
| Scenario | 素材流程 | 资产变体与成套风格 | 游戏美术与工作流 | 素材工作流，不等于玩法测试 | 素材与 REST API |
| 游芽当前 | 四种固定 Canvas 模式 | 自然语言、受控参数、版本差异 | 尚非完整游戏美术生产线 | 构建、浏览器检查、证据、回退；真实模型效果仍待验证 | 本地试玩、源码与证据 ZIP |
| 游芽规划 | 增加五类基础玩法 | 多文件与明确扩展点 | 内置、上传、单一图片 API | 各类型专用验收、人工检查项 | 完整资源与源码导出；未规划首期公网发布 |

游芽两行分别依据当前 README 和专项计划，不能合并为“已经支持”。当前说明还显示本地使用门槛；专项计划明确首版排除任意外部游戏仓库导入、自由源码编辑、3D 与多人联网。[15][16]

## 5. 对定位的修正

推荐定位：**面向独立创作者和小团队策划的 2D 网页游戏原型工作台，让明确的玩法更快变成可试玩、可连续修改、可交接的项目。**

这一定位需要回答三个替代问题：为什么不用 Rosebud 快速生成并分享；为什么不用 GDevelop 直接在引擎里改；为什么不用通用编码 Agent 配合 Phaser 模板。

建议将回答限定在可验证结果：

1. 用户不需要反复描述已经确认的规则，修改目标与保留项可追踪。
2. 多次修改后，旧玩法回归更少，出错时更容易恢复。
3. 用户能知道哪些验收通过、哪些未覆盖、哪些需要亲自试玩。
4. 交付源码、依赖、素材与对应证据能在新环境复现。
5. 达到可用版本的总成本和人工介入次数具有竞争力。

上述均为待实测假设。八角色、多模型、本地运行和中文界面可以解释实现方式或适用人群，不能直接证明用户收益或商业壁垒。

## 6. 从竞品转化出的功能优先级

| 建议 | 具体用户行为 | 参考产品 | 纳入时机 | 可观察的验收 |
| --- | --- | --- | --- | --- |
| 模板对应可试玩示例和支持边界 | 先试玩塔防样例，再描述变化 | Rosebud、GDevelop | 对应类型上线时 | 用户能辨认哪些机制已支持 |
| 变更目标与保留项 | 增加冰冻塔，同时保留箭塔数值和波次 | GDevelop | 塔防完整闭环 | 旧机制断言不因新增功能失效 |
| 参数直接调整 | 将波次数量从 5 改到 8 | GDevelop、Astrocade | 每种类型同步交付 | 无需完整角色流程，仍经过必要验证 |
| 任务级可玩恢复点 | 失败后回到上一版继续修改 | GDevelop、Replit | 工程与版本基础阶段 | 源码、素材、配置与预览一致 |
| 玩法证据与测试回放 | 查看一次重开、建塔和胜负判定 | Replit | 各类型验收阶段 | 结果对应当前版本；未测项明确 |
| 风格说明与素材绑定 | 只替换某座塔外观 | Ludo.ai、Scenario | 基础引用早做，生成 UI 后做 | 命中区域、数值和其他资产未误改 |
| 单轮和累计费用 | 生成前知悉预计费用，失败后看总支出 | Replit、Scenario、Ludo.ai | 付费工具接入前 | 重试、修复、素材支出均入账 |
| 有限范围试玩反馈 | 测试者指出某波过难并关联版本 | Astrocade、SOON | 原型稳定后的小规模试用 | 反馈能转为具体修改和再次验证 |

暂不因此新增：公共社区、素材交易市场、通用节点编辑器、3D、多端商店发布、任意外部仓库导入和大量模型供应商。这些可能有价值，但属于另外的产品投入。

已有阶段计划应调整依赖：多文件查看、资源引用和恢复点属于工程基础；每类玩法的参数、修改和验收应随该类一起交付。无需等五类全部完成才验证塔防用户场景，也不宜把关键迭代交互全部延后到收尾阶段。

## 7. 竞争验证实验

首轮建议优先选择游芽、Rosebud、GDevelop 和 Replit。理由是分别对应本项目、直接浏览器竞品、游戏引擎竞品和通用 Agent 替代方案。SOON 在完成产品访问核验后加入国内对标；素材供应商另做素材实验，避免与整款游戏评分混在一起。

使用同一份中文目标规格，各平台可按其推荐方式操作，但记录模板、模型、套餐、所有提示词及人工修改。中文体验作为单独指标；若使用英文翻译，应单独报告，不能混入中文结果。比较的是端到端产品结果，不能把模型差异忽略后归因于 Agent 架构。

建议任务链：

1. 创建固定路线塔防：两种塔、五波、金币、基地生命、胜负和重开。
2. 调整参数：增加波次，保留已有塔配置和交互。
3. 增加机制：冰冻塔减速，并定义是否叠加、持续时间与免疫行为。
4. 替换素材：换塔和敌人的美术，保留战斗数值和命中判定。
5. 检查原有机制并定位缺陷；平台允许受控植入同类缺陷时，单列修复实验，不与自然缺陷混算。
6. 回到指定历史版本，核对规则、素材和配置，再继续一轮修改。
7. 按其公开支持方式交付，验证站内分享、打包与源码迁出，分别记录，不能统一当成同一种导出。

| 指标 | 统计口径 |
| --- | --- |
| 首个可玩时间 | 从提交规格到预定义核心规则全部可操作，包含等待和人工处理 |
| 总完成时间 | 整条任务链的墙钟时间，并分开记录人工时间 |
| 规则通过率 | 通过的固定断言数 / 固定断言总数；失败和未覆盖分别显示 |
| 修改保留率 | 修改后仍通过的既有断言数 / 修改前通过的既有断言数 |
| 人工介入 | 澄清、纠错提示和手改代码分别计数 |
| 恢复正确性 | 对指定版本的规则、配置、素材及后续编辑分别检查 |
| 交付可复现性 | 新环境下是否能按说明运行，记录缺失资源、密钥和托管依赖 |
| 可用版本成本 | 所有尝试、修复、测试和素材费用；订阅门槛与单次消耗分开 |
| 试玩评价 | 独立试玩者按相同量表评规则清晰、操作、节奏与反馈；不当作自动验收 |

第一轮单次跑通只用于发现问题，不用于发布优劣排行榜。若要比较稳定性，每个产品应做重复运行并保留全部结果，随后增加平台跳跃任务验证结论能否跨类型成立。验收条目由固定规格和人工检查决定，不让各平台自行改写通过标准。

既有 100 元和图片最多 10 次的限制，针对此前集成验证，不自动扩展为竞品订阅预算。本报告不产生订阅或付费游戏生成；后续先确认各平台免费额度能完成哪些任务，再单独核算完整实测成本。

## 8. 商业与交付判断

公开资料支持“这个方向已有产品供给”，不支持“需求已被证明”“市场仍有巨大空白”或“游芽必然能收费”。缺少用户访谈、付费意愿和复用行为证据时，不宜给出市场规模或收入预测。

优先访谈两类人：最近做过 Web 游戏原型的个人开发者；需要向程序或团队交付玩法原型的策划。观察他们是否愿意带着第二个真实需求回来，而不只记录一次演示的满意评价。

本地自带模型接口可以降低平台代付复杂度，但安装、Docker、资源管理和故障支持仍然有成本。若以后服务普通爱好者或教育用户，托管运行、分享和账号体验会成为独立的一轮产品建设。

真正的下一步是用塔防连续修改实验检验产品假设，再决定扩充模板、素材供应商或发布能力；竞品清单应帮助收敛优先级，而不是将各家功能全部累加进当前版本。
