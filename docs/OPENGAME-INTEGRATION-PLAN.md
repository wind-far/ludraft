# 游芽 × OpenGame：多类型游戏工作台修订计划

更新日期：2026-09-14。状态：V0.1 实施中；固定响应 CLI 修复链、模型/构建期间取消、CLI 与诊断构建的持久化及重启清理已通过实测；执行诊断、费用与资源记录已接入模型设置和帮助面板，并通过真实浏览器检查。真实模型调用、工作流接入及完整游戏流程尚未完成。

本文件整合本次讨论中的目标、选项和评审修正，是 OpenGame 集成的专项计划。既有 `plan.md`、`upgrade-plan*.md` 是历史规划，不作为本次能力已实现的依据。当前事实以 `studio/`、`frontend/src/Studio.tsx`、`runner/` 的实现为准。

## 1. 产品目标与已确定的边界

面向个人创作者、策划和具备基础技术能力的开发者，支持通过自然语言生成、试玩、修改和导出单人 2D 网页游戏。游芽负责用户流程与交付治理，OpenGame 负责新类型工程的代码实现与调试。

已确定：

- 保留八角色协作、方案确认、审查、测试、版本回退和本地部署模式。
- 覆盖 OpenGame 五类模板：塔防、平台跳跃、俯视角、网格逻辑、UI 驱动；原 Canvas 三消、接物、躲避、点击链路继续可用。
- 素材支持内置、上传、AI 图片生成。AI 图片提供制作过程中确认清单后生成、素材库独立生成后选用两个入口。
- 图片接口首先支持一种经过真实验证的 OpenAI 兼容图片协议；服务商地址、模型和密钥独立配置。
- 首轮真实验证累计预算按 100 元估算上限控制，图片最多 10 次生成尝试（失败请求也计入）。预算不是确保完成全部评测的保证。
- 首版不包含多人联网、3D、Unity / Unreal、任意依赖安装、AI 视频与音频生成、公网发布、账号计费、可视化关卡编辑器和任意外部游戏仓库导入。
- 源码以浏览、差异和导出为主；修改入口是自然语言与受控参数面板，首版不新增网页内任意源码编辑。

支持等级分开描述：

1. **基础玩法支持**：模板、参数、扩展点、固定规则和专用验证明确。
2. **扩展玩法试验**：在已登记的扩展点内组合新机制，列出缺少的自动验收覆盖。
3. **自由需求探索**：先判断能否落到现有模板；不能实现的机制说明差距，提供缩减需求或新模板研发建议，不强行映射。

“基础模板已验证”不代表“每次模型生成都成功”。正式支持的是明确列出的功能边界；生成效果另以全部实测记录说明。

## 2. 整体功能规划

| 模块 | 本轮交付内容 | 后续扩展 |
| --- | --- | --- |
| 创作入口 | 五类入口、中文需求、材料引用、基础/实验模式、已有作品继续修改 | 更丰富的子玩法与可检索案例 |
| 玩法方案 | 目标、规则、操作、关卡范围、模板能力核对、验收条目、确认修订 | 多关卡与平衡性辅助设计 |
| 团队协作 | 模板感知的八角色、结构化交付、编码分工、澄清与返工 | 根据已验证收益调整角色调用频率 |
| 编码执行 | OpenGame 受控读取、修改、工具反馈、修复、取消、用量记录 | 验证后优化上下文和任务并发 |
| 工程管理 | 多文件清单、业务文件增改删、文本差异、资源预览、参数修改 | 可视化编辑与更多引擎另立项目 |
| 素材中心 | 内置、上传、AI 图片；规格、预览、选用、替换、版本引用 | 图集工具与更多图片供应商 |
| 构建试玩 | 固定依赖构建、Phaser 资源加载、真实工作台 iframe 试玩 | 性能分档与更多设备支持 |
| 验收中心 | 通用检查、五类专用检查、证据、人工检查项、实际失败记录 | 更多子玩法自动检查及质量评测 |
| 版本交付 | 不可变快照、历史对比与试玩、回退、复制、完整源码与资源导出 | 用户明确请求后再规划托管发布 |
| 运行设置 | 模型与图片独立连接、执行器诊断、资源限制、预算账本 | 服务商账单对账与团队管理 |

主要用户流程：

```text
选择类型或描述需求 → 确认玩法、边界与验收
→ 主程/美术/UX 交付 → 选择或生成素材 → 锁定本轮素材
→ OpenGame 编码 → 审查与工具验证 → 必要时有限修复
→ 生成可试玩版本（显示人工验收状态）
→ 试玩反馈 → 新修改任务 → 对比 / 回退 / 导出
```

默认使用内置素材，无额外生成确认。选择 AI 素材时才显示生成清单及预留费用；素材库生成不锁住游戏项目，只有将素材用于某轮制作时才建立不可变引用。

## 3. 五类基础玩法与测试矩阵

| 类型 | 基础玩法范围 | 专用自动检查 | 人工重点 |
| --- | --- | --- | --- |
| 塔防 | 固定路线、建塔、升级、金币、波次、基地生命 | 建造扣费、非法位置拒绝、射程与伤害、击杀奖励、漏怪扣命、波次完成、胜负、重开 | 路线可读、塔可操作、完整一局节奏 |
| 平台跳跃 | 左右移动、跳跃、固定平台、危险物、终点 | 起跳/落地、平台碰撞、越界死亡、到达终点、重开、完整可达路径 | 手感、镜头、落点可辨、关卡可达 |
| 俯视角 | 移动、瞄准射击、敌人追逐、生存波次 | 输入与移动、命中伤害、敌方伤害、出生与清理、波次、胜负、重开 | 目标与危险辨识、操作冲突、节奏 |
| 网格逻辑 | 推箱子、墙体、目标格、关卡重置 | 走格与阻挡、推箱合法性、禁止穿透/连推、目标判定、预设解法、重置 | 规则理解、关卡是否可解、反馈清晰 |
| UI 驱动 | 单人回合制卡牌战斗 | 选牌、费用、效果、无效操作拒绝、敌方回合完成、胜负、重开 | 卡面可读、状态一致、无回合卡死 |

基础预设以单关/单局为验收单位。不能从模板存在多场景能力推导出已支持任意多关卡设计。不同规则的实验玩法使用匹配的验证器；没有适用验证器时只能通过通用检查，不继承基础玩法验证标签。

通用自动检查：构建成功、入口与依赖资源可加载、游戏确实渲染、页面无未处理错误、开始与重开、无外部资源依赖、关键输入能产生可见变化。固定测试不得由生成代码修改。

状态读取与鼠标/键盘输入、画面变化、独立规则断言相互印证；不能仅检查生成代码自己报告的胜利、分数或测试通过字段。测试桥接不出现在普通玩家操作入口，不允许代替真实核心交互。

## 5. 关键技术决策

### 5.1 模板注册与工程快照

- 将游戏引擎、模板族、玩法预设、执行器和验证器分别建模。现有前端 `engine` 字段表示工作流（例如 `team8`），不能直接复用为 Phaser/Canvas。
- 注册表固定 `template_id`、模板版本、游戏引擎、玩法标识、参数 schema、允许的文件操作、可信构建配方和验证器版本。
- OpenGame 起始审查基线为提交 `c9bea37`。V0.1 记录完整提交 SHA、构建产物摘要及实际补丁；禁止运行时自动拉取最新版本。
- Phaser 使用固定依赖与系统构建命令。业务代码可在模板扩展点内新增/修改/删除；基础引擎类、构建脚本、依赖、验证器、系统桥接受保护。
- 场景注册和资源清单从经过校验的声明生成，避免 Agent 为新增场景改写整个系统入口。
- 工程清单记录文本和二进制文件的路径、大小、摘要、角色以及来源；拒绝越界路径、符号链接、重复/冲突操作，按候选副本原子应用变更。
- 审查和生成上下文按相关文件、依赖和任务范围分批读取，保存实际覆盖范围；不能为了迁移多文件而把全部源码重复送给全部角色。
- 最终复验前冻结候选，绑定源码摘要、素材摘要、构建产物摘要、模板及验证器版本。发布同一份被验证产物；若源码或素材变化必须重新验收。
- 旧作品按旧规则解析。旧证据不补造新字段、不冒充新体系验收；历史重建使用对应依赖与构建配方，历史试玩优先直接使用保存的产物。
- 新增 schema 迁移版本，备份后幂等迁移。旧项目不自动切换引擎；跨引擎/类型通过“基于需求创建新项目”完成，不暗示自动移植源码。

### 5.2 Phaser 构建与真实预览

- 旧 Canvas 预览继续保留五文件规则；新 Phaser 工程按可信版本清单提供静态产物。图片 data URL 仅用于 Phaser 内置纹理；脚本和网络请求仍限定在当前版本路径。
- 仅提供发布根目录内的产物，使用明确 MIME；Vite 与 Phaser 相对路径须在 `/v/{version_id}/` 下正确工作，导出后也可用本地 HTTP 服务运行。
- 保留独立预览来源和 iframe 隔离，按实际资源加载需要配置 CSP/CORS；考虑 sandbox 产生的不透明来源，不能只把策略改成 `self` 就假定可用。
- 允许加载当前版本资源不等于允许任意公网网络访问；管理接口和模型代理不能成为游戏页面的可访问资源。
- QA 必须覆盖真实工作台中的 iframe，检查图片、JSON、样式和构建 chunk 加载。容器测试服务器、预览服务与导出服务采用一致的产物结构。
- 构建工具使用受信任配置，不执行候选项目自行提供的 npm scripts、Vite 插件或任意预处理命令。

### 5.3 八角色与 OpenGame 的交付边界

| 角色 | 新体系中的主要交付 |
| --- | --- |
| 制作人 | 用户目标、范围、取舍、交付边界；最终接受交付不代替用户人工试玩 |
| PM | 任务依赖、执行范围、素材等待点、返工路由 |
| 策划 | 可实现的游戏规则、参数、关卡约束、逐项验收 |
| 主程 | 模板选择依据、场景/实体、配置、真实扩展点、文件分工和审查 |
| 美术 | 素材用途、尺寸/帧/透明度规格、风格与素材清单；调用素材服务不隐含额外生成授权 |
| UX | 操作、HUD、开始/结束/重开、反馈与可用性 |
| 程序 | 使用 OpenGame 实现明确任务，返回真实文件变更和未解决问题 |
| QA | 测试选择与实际证据分析、人工检查项、复测结果 |

OpenGame 接收：确认方案及版本、工程清单、任务分工、相关交付、模板 API/设计规则/调试协议、选定素材和真实失败证据。禁止将其退化为只收到短提示词的通用 CLI，也不让它覆盖用户确认的策划结论。

分类、GDD 等上游工具若停用，其必要知识由游芽交付替代。更新旧的角色提示和工作流限制，同时保留旧模板各自的规则快照。

### 5.4 执行器与修复限制

- 首选固定 CLI + `stream-json`，通过专用 MCP 工具访问受控文件操作和验证服务。此选择必须在 V0.1 用真实工具调用验证。
- SDK 不是默认绕过方案；如果 CLI 的工具授权或事件协议无法满足要求，先记录阻断证据和所需最小适配补丁，再调整接口，不能悄悄降低隔离条件。
- Agent 容器通过受控工具按需读取候选文件，内置模板与上游文档只读；不挂载游芽仓库、用户主目录、真实模型配置或 Docker socket。系统设置和环境显式构造，不继承用户 `.qwen` 中的工具或扩展。
- 容器使用 `network=none`，CLI 的 loopback HTTP 仅通过固定 stdio 转发程序访问本轮 MCP 工具和模型代理。后端直接转入任务专用 ASGI 应用，无需向容器暴露宿主管理端口或额外网桥。代理持有服务商密钥、限制目标和模型、计量请求；Agent 不具有任意 shell/网络/外部 MCP 工具。
- 工具服务根据任务身份限定候选目录和操作；固定 runner 由调度服务启动，不能把宿主执行能力交给 Agent。
- 首版每个 Phaser 候选工程串行编码，全局先允许一个 OpenGame 工程运行；模型调用仍受预算和并发约束。
- 初始保护默认值：单次 OpenGame 执行最多 20 个模型轮次、10 分钟；每个开发任务最多 6 次诊断构建/测试，以及最多 3 次由游芽发起的最终验收（初次 + 两轮返工）；全任务主动执行时间最多 30 分钟。V0.1 用记录校准，等待用户和排队不计入主动执行时间。
- 构建/语法/局部逻辑问题在程序执行中修复；涉及已确认玩法变化时停止编码、更新方案并重新确认，原确认失效。
- 网络重试、内部调试和外层返工使用不同计数；所有实际模型及图片调用计入同一预算。额度不足、缺少上下文或工具上限到达均返回可解释的未完成原因，不标记成功。
- 取消终止整棵受管进程及关联容器。执行中的服务重启标为中断，保留候选和记录，首版不伪造无缝续跑。

### 5.5 素材规格与等待状态

- 素材分为背景、图标、卡面、静态角色、内置动画帧组。AI 首版生成前四种；固定动画不自动替换为单张图片。
- 内置资源选择自制或明确可分发的资源，保存来源和许可；不默认重用上游展示游戏中的品牌角色或第三方素材。
- 上传支持 PNG/JPEG/WebP；建议初始上限单文件 8 MB、4096×4096 像素、一个项目引用资源 100 MB。解码在受限进程进行，验证真实格式并拒绝超限像素，限制本地总量。
- 记录宽高、透明通道、用途、资源键、版本、来源；标准化裁切/缩放不改动原件，保留导出用衍生资源。角色贴图与碰撞体分开定义，替换美术不自动改变玩法碰撞。
- 需要透明背景但服务未提供时，标记待处理或由用户改选素材；不承诺仅靠提示词保证抠图质量。
- AI 接口按实际 `images/generations` 请求及 URL/base64 响应做能力验证；记录支持尺寸与参数。下载做大小、格式、重定向和地址校验，保存本地内容后再选用。
- 生成任务独立保存：待开始、生成中、成功、失败、取消/中断。取消不等于供应商停止计费，已发出的请求保留预算占用直至有可靠结果。
- 开发任务需要用户选素材时，使用持久化等待状态并保存方案修订、待执行阶段及素材清单；等待不占进程并发槽，但仍锁定该项目的开发任务。
- 扩展活跃任务唯一约束及恢复逻辑，防止等待素材时同项目启动第二条开发任务。素材清单变化使依赖它的设计/代码交付失效并重新执行相关阶段。
- 锁定后使用不可变素材版本。删除素材库条目仅隐藏入口；历史作品引用仍可读取和导出，物理清理只针对无引用资源。

### 5.6 交付状态、接口和预算

开发任务执行状态、版本自动检查结果、人工验收状态独立保存。任务执行成功表示系统完成本轮流程；版本可显示“自动检查通过，人工待验”。人工不通过保留原快照，产生新的修改需求；不能篡改自动证据。

最小接口扩展：

| 接口职责 | 计划变化 |
| --- | --- |
| 模板发现 | 查询类型、预设、支持等级、参数及环境需求 |
| 创建与方案 | 可选类型/预设；确认绑定方案修订、模板和素材选择 |
| 工程读取 | 文件清单、按需文本与资源读取，避免一次响应返回整个工程 |
| 素材管理 | 独立上传、库内检索、生成任务、选用及不可变引用 |
| 执行器设置 | 独立连接、工具能力诊断、版本和运行限制 |
| 运行事件 | 编码/工具/素材/预算/等待/错误事件，支持重连与重复事件去重 |
| 验收记录 | 逐项自动证据、人工结论、来源版本和工程摘要 |
| 预算账本 | 上限、已知费用、预留、待确认费用、模型和图片请求记录 |

保留旧路由语义，以增量 schema 和兼容层迁移；大型源码与图片响应采用分页/按需加载。新增失败类型至少区分配置、协议、越界操作、构建、玩法检查、资源、预算、超时、取消和中断。

费用策略：

- 100 元是首轮实测预算，不计为免费调用。配置实际输入/输出/缓存 token 及图片单价后才启动付费验证。
- 最小预算账本在 V0.1 首个付费调用前建立；可先以串行调用和人工核账执行试验，不能先花费、到最后才补计量。
- 建议分配：V0.1 预留 15 元，后续编码及修改预留 65 元，图片与故障余量预留 20 元，累计不超过 100 元；内部未消费额度可调整，不能自动扩大总额。
- 每次调用前按可执行的输入输出限制做保守预留，并发预留必须原子化。长上下文的多轮调用逐次预留，不能仅在整个 Agent 会话开始时估一次。
- 供应商超时、用量缺失或请求结果未知时保留待核账额度，重试再次预留。超过图片数量上限即停止生成，失败请求也计入尝试数量。
- 显示估算及其价格依据；服务商未提供硬配额时，不声称实际账单有绝对硬上限。

## 6. 版本迭代计划与验收门槛

本节依据竞品调研重新排序，替代此前阶段 0–6 的串行排期。V0.1–V1.0 是本专项的规划标签，不代表当前软件版本或已经完成的发布。技术仍沿用现有 React/Vite、FastAPI、SQLite 和 Docker，通过兼容层扩展，不迁移整套架构。

首个产品里程碑是“塔防能创建、连续修改、回退与导出”。五类目标保持不变，后续按类型分批实现。已有角色流程、参数修改、版本和导出优先复用；新增投入集中在多文件工程、游戏资源、玩法扩展点和专用验收。竞品已有计划和回退机制，是否更可靠必须用任务结果证明，见 [竞品报告](AI-GAME-WORKBENCH-COMPETITIVE-RESEARCH.md)。

### V0.1：现有链路核验与 OpenGame 接入验证

用户结果：内部开发者能确认模型和执行器真正能完成一次受控修改，明确后续接入的技术依据。

按顺序做：

1. 保存当前工作区基线和已有数据的可恢复副本，区分既有修改与本专项变更。执行相关旧模式回归；用最小真实需求验证当前创建和修改链路，记录真实模型未覆盖的路径。
2. 固定模型、模板和 OpenGame 源码版本；建立最小费用预留与调用记录，核实实际价格。
3. 验证 A：先用小工程验证受控读写、流式事件解析、工具错误反馈、有限修复、取消与超时。避免一开始把 Phaser 资源失败和执行器失败混在一起。
4. 验证 B：固定塔防工程，用内置素材验证构建与真实工作台 iframe 资源加载；让真实 Agent 修改一种塔行为，并复核修改结果。

主要涉及执行器适配、模型路由、最小诊断工具和试验用 runner。不开工重做八角色或正式制作完整素材中心。

进入 V0.2 的门槛：真实读取→修改→错误反馈→修复→试玩有记录；取消有效，旧项目不被破坏；固定资源能在实际 iframe 加载。一次成功只证明接入路径可行，不证明模型质量稳定。

开工时登记 PoC 的工程投入上限；出现同类反复失败或额度耗尽时输出原因和选择，不无限调试。OpenGame 默认仍是执行器候选；若指定模型接口不兼容，先评估有限适配补丁。若必须改变既定执行器路线，先给出具体证据和备选方案。没有凭据时，固定工程、协议和失败测试可以继续，真实接入状态保留待验。

### V0.2：塔防完整创作与连续修改

这是第一个可交给目标用户试用的产品版本。使用可分发内置素材，先验证玩法迭代价值。

基础工程与产品流程必须同批完成：

- 模板注册：区分类型、模板版本、运行引擎、执行器和验证器；旧四种 Canvas 模式保留。
- 多文件增改删与原子应用：支持业务场景、实体、配置文件；保护模板核心、依赖和验收代码。文件树、按需读取和差异展示同步适配。
- 资源清单：建立资源 ID、来源、规格、用途与版本引用；预览按可信构建清单提供图片、JSON 和脚本。源码、素材与产物共同进入快照和导出。
- 塔防基础玩法：固定路线、两种基础塔、建造与升级、金币、五波默认配置、基地生命、胜负与重开；复杂寻路和自由路线编辑暂不开放。
- 修改目标与保留项：从已确认规则中生成本轮变更摘要；仅在需求矛盾或超出范围时补充确认。简单参数调整走短流程，不要求每次完整调用八角色。
- 塔防参数面板：伤害、射程、建造费用和波次配置；规则、配置与界面显示一致。
- 塔防专用验证：建造扣费、非法位置拒绝、升级、伤害、击杀奖励、漏怪扣命、波次、胜负、重开；将未覆盖项与人工待验分开。
- 失败保护、版本回退和导出重建：回到旧版时同时恢复规则、资源与配置；恢复后可以继续修改。
- 审查、修复、独立测试等直接影响该闭环的入口同步适配，不能仍只读三个文件却称完整检查。

验收使用同一作品连续完成：创建塔防→改波次和数值→新增冰冻塔并保留原塔规则→检查旧机制→回退→再次修改→导出后独立运行。冰冻机制的时长、叠加与免疫规则先固定，不能只检查“出现了一座新塔”。

至少完成一条真实模型任务链和人工试玩记录才进入用户试用；保留全部尝试，并标为小样本验证。旧四模式的创建、修改、试玩和导出不得回归。首次可玩时间、人工纠错次数、修改前后规则通过情况和累计费用从本版开始记录。

### V0.3：素材可控替换与单一图片生成

用户结果：可以给已有可玩游戏换外观，并保留规则和历史版本。

先交付不依赖付费生成的部分，再接入图片能力：

1. 上传 PNG/JPEG/WebP、预览、规格检查、受控尺寸处理和素材列表；延续 V0.2 的引用机制。
2. 项目风格说明：参考图、色板、视角、比例；素材清单显示“是什么、用在哪里、需要什么尺寸”。
3. 候选比较与选用：生成结果先作为候选资源，选用后才建立本轮引用；保留旧素材。
4. 局部替换：选择某座塔、某类敌人或背景，更换资源时检查比例、加载和显示。素材替换默认不改伤害、费用、碰撞与玩法参数。
5. 连接一种真实验证过的 OpenAI 兼容图片 API，支持制作过程中的清单生成和素材库独立生成两个入口。
6. 生成前费用预留，支持取消、失败重试、待选用状态恢复；超时结果未知时保留待核账状态，防止重复生成和重复扣费。

验收：同一塔防分别选用内置、上传和 AI 图片；规则检查继续通过；历史版本素材正确；导出不依赖临时供应商 URL。生成失败时可改选内置素材完成游戏修改。真实调用、生成规格和人工视觉检查分开记录。

首版只支持背景、静态角色、图标、卡面等；不承诺图片生成能自动产出稳定的行走/攻击动画。Ludo.ai、Scenario 等列为未来供应商候选，不立即订阅或同时接入。

依赖 V0.2 的多文件与资源基础。图片接口暂缺不阻断 V0.4 的内置素材开发，但本版 AI 部分不能标为完成，V1.0 全范围验收仍需补齐。

### V0.4：平台跳跃，验证跨类型复用

用户结果：能创建和持续修改第二种交互差异明显的游戏。

交付固定平台关卡、左右移动与跳跃、危险物、死亡重置、终点、镜头基础行为；同步交付参数面板、模板说明、角色协议、资源适配和专用检查。验证移动/跳跃输入、起跳落地、碰撞、越界、死亡、终点和重开。

真实任务链至少包括创建→调整跳跃参数→增加一种明确机制→复核原有碰撞与通关→回退→导出。自动可达性先针对固定关卡和已知路线；自由生成地图需要另加求解或人工可达性验证，不能套用固定路线结果。

通过条件：平台跳跃独立完成固定样例测试、真实任务链和人工手感检查；塔防与旧模式仍可用。只有跨类型证据通过，才将公共组件视为可复用基础。

按 V0.5.1 俯视角→V0.5.2 网格逻辑→V0.5.3 UI 驱动小版本交付，避免三个入口同时开放但不可完成。
